# Этап 1 — статус и находки

Соответствует разделу 16 ТЗ: «LLMTranslateKit, Keychain, OpenAI-совместимый
адаптер со стримингом, определение языка, санитизация, минимальные
настройки». Выход: рабочий перевод текста.

## Что сделано

- `LLMTranslateKit` — framework-таргет, линкуется в `LLMTranslate` (app) и
  `LLMTranslateTextExt` (extension).
- `TranslationProvider` (раздел 6.1 ТЗ) + `TranslationRequest`/`Payload`.
- `KeychainStore` (раздел 5 ТЗ) — общая access group, `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`,
  `kSecAttrSynchronizable=false`, маскированный превью.
- `LLMTranslateSettings` — несекретные настройки в `UserDefaults(suiteName:)`
  через App Group `group.com.tyrex.llmtranslate`.
- `LanguagePairResolver` + `LocalLanguageDetector` (раздел 7 ТЗ, все ветви
  алгоритма) — резолвер чистый и тестируемый отдельно от `NLLanguageRecognizer`.
- `PromptBuilder` + `ResponseSanitizer` (раздел 8 ТЗ).
- `OpenAICompatibleProvider` (раздел 6.2/6.4 ТЗ) — стриминг через
  `URLSessionDataDelegate` (не `AsyncBytes.lines`, чтобы граница разрыва
  чанка была под своим контролем и тестируемой), retry на сетевые
  ошибки/429/5xx с экспоненциальной задержкой, без ретрая на 401/403,
  таймауты (8 с/30 с по умолчанию, конфигурируемые).
- `SettingsView` — минимальный экран: провайдер/URL/модель/ключ/языки,
  «Сохранить», «Проверить» (раздел 12, экран 2 ТЗ — тестовый перевод).
- `TranslateSheetView` в `LLMTranslateTextExt` теперь делает **настоящий**
  перевод через Kit вместо реверса текста из этапа 0.
- 52 юнит-теста (раздел 14, пп. 1, 2 частично, 3, 4, 5 ТЗ) — санитизация,
  SSE-парсинг (нормальный поток / разрыв на границе чанка / ошибка в
  середине / обрыв соединения), языковая пара (все ветви), маппинг ошибок,
  Keychain (запись/чтение/удаление/эмуляция «второго процесса»).

## Живая проверка на симуляторе (iPhone 16 Pro, iOS 18.6)

Реального API-ключа в этой сессии нет — проверено то, что можно проверить
честно без него, плюс один реальный сетевой запрос к настоящему
`api.openai.com` с заведомо недействительным тестовым ключом:

1. Экран настроек открывается, дефолты (`https://api.openai.com/v1`,
   `ru`/`en`) подгружаются из `UserDefaults` через App Group.
2. «Проверить» без сохранённого ключа → `TranslationError.missingAPIKey`
   → «Не задан API-ключ» — реальный путь через `KeychainStore.apiKey()`,
   возвращающий `nil`.
3. Ввод модели (`gpt-4o-mini`) и тестового ключа (`sk-test...`), «Сохранить»
   → превью показывает `sk-…cdef` — подтверждён реальный
   `SecItemAdd`/`SecItemCopyMatching` через Security framework на
   устройстве (не мок).
4. «Проверить» с этим (заведомо недействительным) ключом → реальный
   HTTPS-запрos к `https://api.openai.com/v1/chat/completions` →
   OpenAI отвечает `401` → корректно замаплено в
   `TranslationError.authenticationRejected` → «Ключ отклонён провайдером».
   Подтверждает: сборку запроса, TLS/сетевой стек симулятора,
   `URLSessionDataDelegate`-стриминг, обработку non-2xx статуса,
   маппинг ошибок — весь путь, кроме собственно успешного перевода
   (для этого нужен настоящий рабочий ключ).
5. То же самое — **из расширения** `LLMTranslateTextExt`: Safari → выделение
   текста → «Перевести» → шторка показывает тот же результат «Ключ отклонён
   провайдером». Подтверждает, что расширение как отдельный процесс реально
   читает ключ, сохранённый приложением, через общую Keychain access group
   (`keychain-access-groups` entitlement) — не просто «то же значение
   entitlement объявлено», а фактическая работа sharing на устройстве.

Локальный сервер-заглушка (для проверки успешного потока без реального
ключа OpenAI) не поднялся — `curl`/`python3 -m http.server` не достижимы
по loopback из инструментов этой сессии (сетевая изоляция песочницы).
Проверка успешного потокового перевода потребовала реального ключа от
пользователя — см. следующий раздел, там она пройдена.

## Успешный перевод — проверено с реальным ключом OpenRouter

Пользователь завёл ключ на openrouter.ai и вставил его сам в симулятор
(не через меня — ключ ни разу не прошёл через этот чат в рабочем виде,
кроме одного случая, когда пользователь сам вставил его в лог curl;
после этого ключ был отозван и заменён).

1. `Проверить` с моделью `google/gemma-4-31b-it:free` и `baseURL:
   https://openrouter.ai/api/v1` → сначала `402` (баланс аккаунта был
   $0 — OpenRouter требует неотрицательный баланс даже для `:free`
   моделей, задокументировано в их доках), затем, после пополнения
   баланса — `429` (`Лимит запросов`, 20 запросов/мин на free-tier,
   исчерпан собственными повторными попытками, усугублёнными
   автоматическим ретраем на 429 в `OpenAICompatibleProvider`).
2. После переключения на платную модель (`openai/gpt-4o`, подтверждено
   пользователем через отдельный `curl`, что ключ и баланс рабочие) —
   **успешный** результат в «Проверить»: «Модель отвечает».
3. То же самое — **из расширения**, живым выделением абзаца в Safari
   (статья Wikipedia про Lepidoptera) и системным «Перевести»: шторка
   показала настоящий переведённый текст, не ошибку.

Стриминг, парсинг SSE, санитизация ответа — весь путь подтверждён на
реальных данных, не только на 401/429.

### Побочная находка: порог определения языка (раздел 7, п. 5 ТЗ)

При тесте с одним выделенным словом ("Lepidoptera", 11 символов)
всплыла проблема: раздел 7 ТЗ называет порог длины текста для доверия
распознаванию в 3 символа, но `NLLanguageRecognizer.h` от Apple прямо
предупреждает, что короче ~30 символов распознавание ненадёжно. Порог
поднят до 30 в `LanguagePairResolver.minimumTextLength` — см. отдельный
коммит `94dbc03`, там же обновлены юнит-тесты.

## Найденный и исправленный краш: `Library not loaded: @rpath/LLMTranslateKit.framework`

При первом запуске расширения через реальный UI (после того как сборка
через `-target`/`-sdk` прошла успешно) расширение падало при старте —
`EXC_CRASH` / `Termination Reason: Namespace DYLD, Code 1, Library missing`.

Причина: `LLMTranslateKit` подключён к `LLMTranslateTextExt` с `embed: false`
(единственная копия фреймворка встроена в `LLMTranslate.app/Frameworks`
хост-приложением) — это осознанное решение, чтобы не дублировать фреймворк
в каждом расширении. Но дефолтный `LD_RUNPATH_SEARCH_PATHS` для
`extensionkit-extension`-таргета у xcodegen — только
`@executable_path/Frameworks` (собственная, пустая, папка расширения).
Путь до Frameworks хост-приложения (`@executable_path/../../Frameworks`)
входит в `LD_RUNPATH_SEARCH_PATHS` официального Xcode-темплейта «iOS
ExtensionKit Extension Base.xctemplate», но xcodegen этот темплейт-дефолт
не применяет сам — его нужно задать явно.

Исправлено в `project.yml` (`LLMTranslateTextExt.settings.base.LD_RUNPATH_SEARCH_PATHS`):
```
$(inherited) @executable_path/Frameworks @executable_path/../../Frameworks
```
После фикса и переустановки — расширение стартует и находит фреймворк
(см. живую проверку п. 5 выше).
